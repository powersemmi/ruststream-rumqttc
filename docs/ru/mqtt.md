# MQTT {#mqtt}

`ruststream-rumqttc` выполняет сервис RustStream на MQTT 5, через
[`rumqttc`](https://docs.rs/rumqttc). MQTT - это шина тем без истории. Крейт покрывает фильтры тем
с подстановочными знаками, качество обслуживания, совместные подписки, сохранённые сообщения,
сессии и последнюю волю, а под фичей `testing` поставляет внутрипроцессный брокер для тестов.
Понятия фреймворка (как писать подписчиков, маршрутизация, кодеки, middleware) описаны в
[документации RustStream](https://powersemmi.github.io/ruststream/).

```toml
ruststream = { version = "0.7", features = ["macros"] }
ruststream-rumqttc = "0.7"
serde = { version = "1", features = ["derive"] }
```

## Совместимости {#capabilities}

Какие из необязательных совместимостей фреймворка этот брокер реализует нативно и что здесь
происходит с подтверждением:

| Совместимость | Нативно | Причина |
| --- | --- | --- |
| `Subscribe` | Да | `MqttTopic` описывает подписку на один фильтр темы. См. [Подписки](#subscriptions). |
| Подтверждение (`ack` / `nack`) | Частично | `QoS` 1 и 2 завершают доставку средствами протокола. `QoS` 0 и `nack(requeue = true)` возвращают `AckError::Unsupported`. См. [Подтверждение](#acknowledgement). |
| `BatchSubscriber` | На стороне клиента | В одном PUBLISH передаётся одно сообщение, поэтому пакеты собирает сам крейт - до размера, названного в точке монтирования. См. [Пакеты](#batches). |
| `TransactionalPublisher` | Нет | В MQTT нет транзакций. |
| `OwnedTransactions` | Нет | В MQTT нет транзакций. |
| `RequestReply` | Нет | У MQTT 5 есть свойство с темой ответа, и крейт сопоставляет его заголовку `reply-to` в обе стороны; коррелированный вызов `request(msg, timeout)` не реализован. Отвечающая сторона - обычный обработчик, который публикует в `ctx.headers().reply_to()`. См. [Заголовки](#headers). |
| `Partitioned` | Нет | В MQTT нет ни партиций, ни ключей маршрутизации; порядок соблюдается в пределах темы на одном соединении. |
| `Seekable` / `Positioned` | Нет | Брокер хранит одно сохранённое сообщение на тему и неподтверждённые сообщения постоянной сессии - больше перематывать не на что. |
| `DescribeServer` | Да | `MqttBroker` сообщает хост и порт, к которым подключается клиент, и протокол `mqtt`; это и записывает схема AsyncAPI. Учётные данные из URL туда не попадают. |

## Жизненный цикл {#the-lifecycle}

Каждое состояние брокера - отдельный тип:

```text
MqttBroker::new(url, client_id)   только конфигурация, синхронно, без ввода-вывода
  .connect()   ->  ConnectedMqttBroker   живая сессия; подписки и издатели
  .shutdown()             ->             штатный DISCONNECT, завершающий задачу соединения
```

`connect` запускает задачу соединения и возвращает управление, когда приходит первый `CONNACK` от
брокера, либо возвращает отказ, который брокер прислал вместо него.

`shutdown` поглощает подключённый брокер, поэтому публикация или подписка после него не
компилируется. Издатель, выданный раньше, переживает соединение и после его закрытия возвращает
`MqttError::NotConnected`, а не отрабатывает успешно на уже закрытой сессии.

Настройки сессии и транспорта заданы на синхронном билдере. `credentials`, `keep_alive`,
`clean_start` и `session_expiry` настраивают сессию, а `last_will` называет сообщение, которое
брокер публикует, если эта сессия оборвалась неожиданно. Умолчание `max_packet_size` - 1 МиБ, выше
собственного предела клиента в 10 КиБ, а `receive_maximum` задаёт управление потоком. `tls_ca` и
`tls_client_auth` покрывают управляемые сервисы MQTT, которые требуют клиентский сертификат.

## Подписки {#subscriptions}

`MqttTopic` описывает одну подписку: фильтр темы, качество обслуживания и необязательную группу
совместной подписки. Он пишется прямо в `#[subscriber(..)]`, а `ruststream_rumqttc::prelude`
реэкспортирует прелюдию самого фреймворка вместе с поверхностью этого крейта, поэтому одного glob
хватает на файл сервиса:

```rust
--8<-- "crates/ruststream-rumqttc/examples/mqtt_service.rs:handler"
```

Приложение называет брокер и монтирует обработчик:

```rust
--8<-- "crates/ruststream-rumqttc/examples/mqtt_service.rs:app"
```

Обработчик, фильтр которого задаёт развёртывание, а не код, пишет вместо этого
`#[subscriber(MqttTopic)]` и берёт фильтр из `.name(..)` в точке монтирования; качество
обслуживания и группа тогда остаются умолчаниями.

Подписчик снимает подписку на свой фильтр, когда его уничтожают.

### Подстановочные знаки {#wildcards}

Подстановочные знаки здесь протокольные: `+` совпадает ровно с одним уровнем темы, `#` совпадает с
остатком темы и стоит только последним уровнем. `MqttMessage::topic` сообщает конкретную тему, в
которую пришло сообщение, а не фильтр, который с ней совпал, поэтому обработчик на
`devices/+/telemetry` читает, какое устройство прислало показание. Подстановочные знаки работают
только на подписке: публикация в тему с подстановочным знаком возвращает ошибку и ничего не
отправляет.

Неверный фильтр возвращает ошибку с именем этого фильтра, до всякого ввода-вывода.

### Качество обслуживания {#quality-of-service}

`Qos` выбирает гарантию доставки, по умолчанию `Qos::AtLeastOnce`:

| Вариант | Поведение в протоколе |
| --- | --- |
| `Qos::AtMostOnce` | Отправил и забыл. Подтверждения для таких доставок не существует. |
| `Qos::AtLeastOnce` | Доставка подтверждается через `PUBACK`. |
| `Qos::ExactlyOnce` | Рукопожатие из четырёх пакетов протокола; вторую его половину выполняет клиент. |

### Совместные подписки {#shared-subscriptions}

`MqttTopic::new("jobs").shared("workers")` подписывается на `$share/workers/jobs`. Брокер делит
подходящие сообщения между участниками группы, а не выдаёт каждому по копии - так MQTT выражает
конкурирующих потребителей. Имя группы принадлежит только фильтру подписки: `filter()` и тема,
сообщаемая при доставке, остаются в простой форме.

Два участника одной группы на одном соединении - для брокера одна подписка, поэтому доставки между
ними крейт раздаёт по очереди. Имя группы, пустое или содержащее `/`, `+` или `#`, возвращает
ошибку до всякого ввода-вывода, как и неверный фильтр.

### Пакеты {#batches}

Пакетный обработчик принимает `&[T]`, а размер называет точка монтирования:

```rust
--8<-- "crates/ruststream-rumqttc/examples/mqtt_batches.rs:batches"
```

В одном PUBLISH передаётся одно сообщение, поэтому пакеты собирает сам крейт. Пакет закрывается,
когда в нём накопился размер, названный в точке монтирования, или через 20 миллисекунд после
первой доставки - что наступит раньше. Размер задаёт точка монтирования, срок задаёт крейт, и
больше своего размера пакет никогда не держит. Простаивающая подписка ждёт первой доставки сколько
угодно, поэтому тихая тема ничего не стоит.

В точке монтирования ничто не говорит, кто наполнил пакет - крейт или брокер, поэтому пакетный
обработчик, написанный для другого брокера, монтируется здесь без изменений. Подтверждение
остаётся по доставкам: пакет, брошенный на середине наполнения, оставляет свои сообщения
неподтверждёнными, и они доставляются повторно, когда возобновляется постоянная сессия.

## Подтверждение {#acknowledgement}

Подтверждение следует качеству обслуживания самой доставки, а доставка завершается, когда
обработчик вернул исход, а не когда сообщение пришло:

- `QoS` 1 и 2 подтверждаются средствами протокола.
- Доставки на `QoS` 0 возвращают `AckError::Unsupported`: подтверждающего пакета протокола для
  них нет.
- `nack(requeue = true)` тоже возвращает `AckError::Unsupported`. Отрицательного подтверждения в
  MQTT нет, а неподтверждённое сообщение доставляется повторно, когда возобновляется постоянная
  сессия.
- `nack(requeue = false)` подтверждает: отбрасывание - единственный завершающий исход, который
  предлагает протокол.

Когда сообщение совпало сразу с двумя пересекающимися фильтрами, подтверждение принадлежит ровно
одной доставке, а копии возвращают `AckError::Unsupported`.

### Что здесь делает исход обработчика {#what-a-handlers-outcome-does-here}

`HandlerOutcome::retry()` просит брокер доставить сообщение повторно, а в MQTT просить нечем.
Рантайм логирует отклонённое отрицательное подтверждение (`ack / nack failed`) и идёт дальше,
поэтому доставка так и остаётся неподтверждённой. На `QoS` 1 и 2 сообщение поэтому возвращается
при возобновлении постоянной сессии - `clean_start(false)`, срок жизни сессии длиннее перерыва и
переподключение - и никогда внутри живого соединения: в секунды после возврата обработчика не
повторяется ничего. На `QoS` 0 повторять нечего, и сообщение потеряно. Читайте `retry()` здесь как
«оставить до следующей сессии», а не как «скоро попробовать снова».

`HandlerOutcome::retry_after(delay)` - исход, который повторяет доставку внутри сессии, средствами
самого фреймворка, а не протокола: дайте точке монтирования издателя повторов через
`retry_via(..)`, и рантайм подтвердит оригинал, выждет, а затем опубликует копию в ту же тему со
счётчиком повторов в заголовках. Подтверждение оригинала - первый шаг этого запасного пути, и ему
нужна доставка, которую можно подтвердить: на `QoS` 0 шаг отклоняется, отложенная копия не
публикуется, и сообщение теряется. Без настроенного издателя повторов рантайм предупреждает и
откатывается к `retry()` с последствиями, описанными выше.

Этой копии нужна тема, а подписка может назвать её только тогда, когда её фильтр - тема. До
подписки на `devices/dev42/telemetry` доходит публикация туда же, и совместные подписки тоже:
группа разбирает копию между участниками. До подписки на фильтр с подстановочным знаком так не
добраться вовсе, потому что `+` и `#` работают только на подписке, поэтому крейт отвечает, что
адрес назвать не может, а не называет адрес, который никуда не ведёт. Область, где `retry_via(..)`
задан над подпиской на фильтр с подстановочным знаком, тогда не запускается и называет эту
подписку: сервис узнаёт на старте, что у `retry_after` здесь нет запасного пути, вместо того чтобы
терять каждое отложенное сообщение на публикации в никуда.

`HandlerOutcome::drop()` подтверждает, потому что отбрасывание - единственный завершающий ответ
протокола. Отправку в dead-letter делает сам сервис публикацией, а не брокер.

Обратное давление здесь - это receive-maximum протокола, который задаёт
`MqttBroker::receive_maximum`: брокер держит одновременно не больше такого числа неподтверждённых
доставок `QoS` 1/2, и это же ограничивает очередь непрочитанного подписчика. У `QoS` 0 такого
предела нет.

## Переподключение {#reconnection}

Крейт владеет задачей, которая опрашивает единственный цикл событий клиента и отдаёт каждый пакет
протокола тем подпискам, фильтры которых с ним совпали. Именно опрос двигает keep-alive,
подтверждения и управление потоком, поэтому подписки и публикации выдаются из задачи вызывающей
стороны, и медленный потребитель никогда не задерживает трафик keep-alive.

Задача переподключается сама, с нарастающей задержкой: она начинается со 100 мс и удваивается до
потолка в 5 секунд. Отказ, который брокер не пересмотрит (неверные учётные данные, неприемлемый
идентификатор клиента), вместо этого завершает задачу, и каждая подписка возвращает эту ошибку.

Что произойдёт с подписками после переподключения, решает флаг `session_present` в `CONNACK`.
Сессия на месте - фильтры по-прежнему зарегистрированы и ничего не отправляется заново; сессии
нет - каждая живая подписка оформляется снова.

## Публикация {#publishing}

`MqttPublish` - политика, которая конструирует издателя, и объявляет она две вещи: качество
обслуживания и флаг сохранения. Она же - политика этого брокера по умолчанию, поэтому обработчик
`#[subscriber(.., publish)]`, смонтированный без собственной политики, отправляет через неё. Ответ
уходит в тему, которую объявляет его собственный тип.

Точка монтирования, которая политику всё же называет, пишет `.out(marker, policy)`:
`.out(Reply, Publish::default().qos(Qos::ExactlyOnce))` - для того, что возвращает обработчик, и
тот же вызов под собственным маркером слота `Out` - для издателя, которого держит тело. Аргументы
в обоих местах задаёт политика, поэтому слот и ответ пишутся одинаково.

Какое имя пишет файл, следует из прелюдии, которую он импортирует. Файл обработчика импортирует
`ruststream::prelude::*` и ограничивает внедрённого издателя трейтом-совместимостью,
`Out<impl Publisher>`, поэтому тело не называет брокерных типов вовсе. Файл маршрутов импортирует
`ruststream_rumqttc::prelude::*`, где политика отвечает на имя `Publish`: точка монтирования тогда
читается одинаково, на каком бы брокере она ни работала, и перенос сервиса меняет импорт, а не
вызов. `MqttPublish` остаётся в корне крейта - для файла, который смешивает два брокера и обязан
сказать, какой из них имеет в виду.

Публикация возвращает управление, как только сообщение принадлежит сессии клиента, а не когда
брокер его подтвердил. На `QoS` 1 и 2 сессия повторяет передачу, пока брокер не подтвердит, в том
числе через переподключения.

Полезная нагрузка MQTT часто - это значение, которое сервис уже держит в байтах (строка состояния,
кадр датчика, запись protobuf), а не модель, которую фреймворку надо кодировать. Тип, объявленный
сериализованным, отправляет эти байты в точности как есть, без кодека на пути, и его объявление
всё равно называет тему. `{placeholder}` в этом имени становится сеттером, который заполняет
вызов:

```rust
--8<-- "crates/ruststream-rumqttc/examples/mqtt_retained.rs:state"
```

### Аргументы отдельного сообщения {#per-message-arguments}

Оба аргумента, которые MQTT передаёт в PUBLISH, - это шаги публикации, и порядок их неважен:

| Шаг | Что задаёт для одного сообщения |
| --- | --- |
| `qos(qos)` | Качество обслуживания доставки. |
| `retain(retain)` | Оставит ли брокер это сообщение сохранённым для темы. |

Аргумент, который вызов не назвал, берётся из политики точки монтирования, поэтому
`Publish::default().qos(Qos::ExactlyOnce)` - умолчание для каждой публикации через этого издателя,
а шаг - то, чем отличается одно сообщение:

```rust
--8<-- "crates/ruststream-rumqttc/examples/mqtt_retained.rs:per_publish"
```

Шаги стоят на самой публикации, а не на отдельном издателе, поэтому публикация с шагами во всём
остальном - обычная публикация: кодируется она кодеком, названным в её точке монтирования, а
публикация в слот остаётся отнесённой к своему слоту, и `tb.out::<Marker>()` записывает её как
любую другую. Шаги доступны везде, где строится публикация: в теле обработчика, в хуке старта, в
тесте.

Значения уходят клиенту как поля протокола, поэтому ни одно из них не отправляется пользовательским
свойством, и подписчик видит обычное сообщение. Публикация без собственного места вызова - ответ
или копия, которую рантайм публикует для отложенного повтора, - берёт политику целиком.

Тело обработчика, которое один из них меняет, - единственное место, где тело называет этот брокер.
Оно импортирует `ruststream_rumqttc::prelude::*` ради шагов и ограничивает свой слот типом
`MqttPublishOptions`, поэтому сигнатура говорит, под какой брокер написано тело:

```rust
--8<-- "crates/ruststream-rumqttc/examples/mqtt_retained.rs:stepped_handler"
```

Умолчания объявляет её точка монтирования, а шаг - то, что меняет одно сообщение:

```rust
--8<-- "crates/ruststream-rumqttc/examples/mqtt_retained.rs:stepped_mount"
```

Тест называет тот же тип, чтобы проверить, с чем ушла публикация:
`tb.out::<States>().assert_called_once().with_options(&MqttPublishOptions::default().retain(true))`,
а `assert_options_default()` - это проверка того, что публикация не взяла ни одного шага.

### Сохранённые сообщения {#retained-messages}

`Publish::default().retain(true)` публикует с сохранением: брокер держит последнее сообщение
каждой темы и отдаёт его каждому новому подписчику с подходящим фильтром. Сервис, который
запустился после того, как устройство опубликовало своё состояние, это состояние всё равно
получает. До совместных подписок сохранённые сообщения не доходят.

Издатель, который сохраняет всё, что отправляет, объявляет флаг один раз в своей политике;
отдельное объявление берёт его на сообщение через `retain(true)`. И там и там хук `after_startup`
области выполняет публикацию, как только брокер подключён:

```rust
--8<-- "crates/ruststream-rumqttc/examples/mqtt_retained.rs:retained"
```

## Заголовки {#headers}

Заголовки уходят пользовательскими свойствами MQTT 5, поэтому крейт не изобретает формат конверта,
и клиенты не на Rust видят обычные сообщения MQTT. Общеизвестные заголовки `content-type`,
`reply-to` и `correlation-id` занимают вместо этого соответствующие штатные свойства (тип
содержимого, тему ответа, данные корреляции), в обе стороны. Сообщение без заголовков публикуется
вообще без свойств: [аргументы отдельного сообщения](#per-message-arguments) - не заголовки, а
поля протокола в самом PUBLISH, и на это правило они не влияют.

Отвечающая сторона - обычный обработчик: у входящего запроса тема ответа задана в заголовке
`reply-to`, обработчик читает `ctx.headers().reply_to()` и публикует ответ в эту тему через
внедрённого издателя.

## Тестирование {#testing}

Фича `testing` поставляет `MqttTestBroker` - внутрипроцессный брокер, который выполняет сервис без
сервера и без сети. Импортируйте его из `ruststream_rumqttc::testing`: прелюдия, которую
импортирует файл маршрутов, - это словарь точки монтирования, и его там нет. Тест монтирует
приложение на этот брокер и прогоняет настоящие обработчики, кодеки и middleware через обвязку
`TestApp` фреймворка. См.
[Юнит-тестирование сервиса через TestApp](https://powersemmi.github.io/ruststream/latest/guides/testing/#unit-testing-a-service-with-testapp).

Пакеты он наполняет так же, как настоящий подписчик: тот же размер из точки монтирования и тот же
срок, поэтому под обвязкой пакетный обработчик получает то, что дал бы сервер.

Файл маршрутов монтируется на него как написан, обеими своими половинами. `MqttTopic` подписывается
на тестовом брокере, поэтому обработчик, который поставляет сервис, - это тот же обработчик,
который монтирует обвязка: тот, что в начале этой страницы, вместе с подстановочным знаком,
качеством обслуживания и группой. `MqttPublish` инстанцирует издателя на нём же, поэтому строка
`b.include(handle).out(Reply, Publish::default())` одна и та же на обоих брокерах.
Внутрипроцессного дескриптора и внутрипроцессной политики на подмену нет; меняется только брокер,
на котором собрано приложение.

Тестовый брокер маршрутизирует по совпадению с фильтром темы - по тому же правилу, по которому
задача соединения разбирает доставки, - поэтому внутри процесса фильтр отбирает те же темы, что и
при передаче, и устройство, публикующее в `devices/dev42/telemetry`, доходит до тела. Дескриптор
проверяется и здесь: фильтр, который отверг бы сервер, не даёт приложению стартовать, а не
проходит свой первый тест.

Остальное в дескрипторе соблюдается настолько, насколько ответ вообще наблюдаем без сервера.
Группа совместной подписки заставляет участников конкурировать: четыре публикации - это четыре
доставки на всю группу, а не по одной каждому участнику, поэтому тест может проверить, что работа
поделена, а не только что она случилась. Качество обслуживания решает, можно ли завершить доставку
(берётся меньшее из публикации и подписки, как и при передаче), поэтому доставка на `QoS` 0
сообщает `AckError::Unsupported` здесь ровно так же, как против Mosquitto, и обработчик не может
втихую доказать гарантию, о которой никто не просил.

Чего внутрипроцессный брокер не воспроизводит - это сам протокол: обмен подтверждениями за
подтверждаемым `QoS`, сохранённые сообщения и сессию, которая доставляет повторно. `retain`
политики по той же причине дальше инстанцирования не идёт: внутри процесса последнее сообщение
темы хранить негде. Поэтому тест на этом транспорте говорит, что обработчик получил, как он
завершил доставку и что и куда опубликовал; а что те же ответы верны и при передаче, говорит набор
тестов против настоящего Eclipse Mosquitto, включаемый переменной `MQTT_TEST_URL`. Повторное
проигрывание сообщений на постоянной сессии - как раз из таких: подписчик, который отключился и
вернулся под тем же идентификатором клиента, получает то, что публиковалось в его тему, пока его
не было, и доказывает это только прогон против сервера.

Контрактные наборы фреймворка прогоняются на обоих. Набор маршрутизации - только внутри процесса,
а последовательность переходов жизненного цикла и набор для пакетной совместимости прогоняются
дважды: против внутрипроцессного брокера и против Mosquitto. Каждый сценарий в
`tests/stand_in_mqtt.rs` - двойник сценария против сервера в `tests/integration_mqtt.rs`, поэтому
поведение, проверенное внутри процесса, прослеживается до подкрепляющего его прогона против
сервера.

Завершение доставки отвечает здесь то же, что и при передаче, вплоть до отказов.
`nack(requeue = true)` внутри процесса сообщает `AckError::Unsupported` ровно так же, как
настоящее сообщение, потому что отрицательного подтверждения в MQTT нет: обработчик, вернувший
`HandlerOutcome::retry()`, повторной доставки под обвязкой не получает, и ни один тест на этом
транспорте не может заявить повтор, которого сервис никогда не получит. Раздел
[«Что здесь делает исход обработчика»](#what-a-handlers-outcome-does-here) описывает это целиком -
и внутри процесса, и против сервера.
