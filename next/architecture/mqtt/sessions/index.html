    Sessions

    An MQTT session holds a client's subscriptions and unacknowledged messages; a persistent one outlives the connection and resumes on reconnect.

    The client id names the session. MqttBroker::new takes it beside the URL, and a second connection with the same id takes the session over.

    Two settings of the CONNECT decide whether the session outlives the connection. clean_start(false) asks the server to resume the session the client id already has. session_expiry says how long the server keeps it after the connection ends, in whole seconds. Without them a connection starts a clean session, which ends with the connection.

    The CONNACK answers whether the server found the session. When it reports none, this crate subscribes every filter again. When the session is present, the subscriptions are still on the server, and the QoS 1 and QoS 2 messages that arrived while the service was away, or that it never acknowledged, come next. Those messages can arrive before the subscription they belong to has opened, so the crate holds up to 1024 of them until it does.

    The keep-alive is the longest silence the connection allows. When nothing else travels, the client sends a PINGREQ, and the server ends a connection that stays silent for one and a half times the interval. rumqttc asks for 60 seconds unless keep_alive names another, and its minimum is 5 seconds.

    The last will is a message the CONNECT leaves with the server. The server publishes it when the connection ends without a DISCONNECT: a crash, a lost network, a keep-alive that ran out. A shutdown sends the DISCONNECT, so a service that stops cleanly publishes no will.

    Two more settings of the CONNECT bound what the server sends. The Receive Maximum is drawn on Quality of service. The Maximum Packet Size is the largest packet the client accepts, and the server discards a message larger than that for this client instead of sending it. This crate announces 1 MiB by default, and max_packet_size changes it. The CONNACK also says whether the server offers subscription identifiers, which Demultiplexing relies on.

    The session is the protocol's own, from sections 3.1, 3.2 and 4.1 of the MQTT 5.0 standard. How this crate opens and closes it is on Lifecycle.
