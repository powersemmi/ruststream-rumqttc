    请求与响应

    本指南回答 MQTT 5 请求：每个答复都发往请求指定的主题，并带上请求的关联数据。

    MQTT 5 为此给请求提供了两个属性。 响应主题说明答复发往何处。 关联数据是一个不透明的值，请求方用它把答复和问题对应起来。 Broker 在两个方向上把它们映射到 reply-to 和 correlation-id 消息头。

    示例是一个设备代理。 控制台在 devices/dev42/config/get 上向它查询某一项设置，它以该设置的值作答。

    应答者​

    • 宏
    • 手写
    src/main.rs
    /// Asks the device for one setting.
    #[derive(Debug, PartialEq, Deserialize, Serialize, Outgoing)]
    #[outgoing(name = "devices/dev42/config/get")]
    struct ConfigQuery {
        key: String,
    }

    /// The answer. The type names no topic: each query says where its answer goes.
    #[derive(Debug, PartialEq, Deserialize, Serialize, Outgoing)]
    struct ConfigValue {
        key: String,
        value: String,
    }

    /// Stands in for the device's settings.
    fn setting(key: &str) -> Option<&'static str> {
        match key {
            "sample-interval" => Some("30s"),
            "firmware" => Some("2.1.0"),
            _ => None,
        }
    }

    /// A query without a response topic is answered on the topic the mount site names; a key the
    /// device does not have gets no answer.
    #[subscriber(
        MqttTopic::new("devices/dev42/config/get"),
        reply("devices/dev42/config")
    )]
    async fn answer(query: &ConfigQuery) -> Result<ConfigValue, HandlerOutcome> {
        let Some(value) = setting(&query.key) else {
            tracing::warn!(query.key, "unknown setting");
            return Err(HandlerOutcome::drop());
        };
        tracing::info!(query.key, "setting reported");
        Ok(ConfigValue {
            key: query.key.clone(),
            value: value.to_owned(),
        })
    }
    src/main.rs
    /// Asks the device for one setting.
    #[derive(Debug, PartialEq, Deserialize, Serialize, Outgoing, JsonSchema)]
    #[schemars(crate = "ruststream::schemars")]
    #[outgoing(name = "devices/dev42/config/get")]
    struct ConfigQuery {
        key: String,
    }

    /// The answer. The type names no topic: each query says where its answer goes.
    #[derive(Debug, PartialEq, Deserialize, Serialize, Outgoing, JsonSchema)]
    #[schemars(crate = "ruststream::schemars")]
    struct ConfigValue {
        key: String,
        value: String,
    }

    /// Stands in for the device's settings.
    fn setting(key: &str) -> Option<&'static str> {
        match key {
            "sample-interval" => Some("30s"),
            "firmware" => Some("2.1.0"),
            _ => None,
        }
    }

    /// A key the device does not have gets no answer.
    struct Answer;

    impl Handle<ConfigQuery, ConfigValue> for Answer {
        fn handle(
            &self,
            query: &ConfigQuery,
            _outs: &(),
            _ctx: &mut Context<'_>,
        ) -> impl Future<Output = Result<ConfigValue, HandlerOutcome>> {
            let Some(value) = setting(&query.key) else {
                tracing::warn!(query.key, "unknown setting");
                return ready(Err(HandlerOutcome::drop()));
            };
            tracing::info!(query.key, "setting reported");
            ready(Ok(ConfigValue {
                key: query.key.clone(),
                value: value.to_owned(),
            }))
        }
    }

    应答者就是带回复的普通处理器：它返回的值会被发布。 ConfigValue 没有指定主题，所以由挂载点指定：reply("devices/dev42/config")。 这个主题是后备主题，用于没有携带响应主题的请求。 设备没有的设置以 drop 结束，不发布任何东西。

    在响应主题上作答​

    • 宏
    • 手写
    src/main.rs
    /// Sends the answer to the response topic of the query, which arrives as the `reply-to` header,
    /// and copies the query's correlation data, so the requester matches the answer to its question.
    struct ToResponseTopic;

    impl<C, Options> PublishTransform<ForReply<C>, Options> for ToResponseTopic {
        type Destination = Names;

        fn apply(
            &self,
            out: &mut Outgoing<'_>,
            _options: &mut Option<Options>,
            cx: &PublishContext<'_, C>,
        ) {
            if let Some(topic) = cx.headers().reply_to() {
                out.set_name(topic.to_owned());
            }
            if let Some(id) = cx.headers().correlation_id() {
                out.headers_mut().insert("correlation-id", id.to_owned());
            }
        }
    }

    #[ruststream::app]
    fn app() -> impl App<State = ()> {
        RustStream::new(AppInfo::new("device-agent", "0.1.0")).with_broker(
            MqttBroker::new("mqtt://localhost:1883", "device-agent-dev42"),
            |b| {
                b.include(answer)
                    .out_reply(Publish::default())
                    .transform(ToResponseTopic);
            },
        )
    }
    src/main.rs
    /// Sends the answer to the response topic of the query, which arrives as the `reply-to` header,
    /// and copies the query's correlation data, so the requester matches the answer to its question.
    struct ToResponseTopic;

    impl<C, Options> PublishTransform<ForReply<C>, Options> for ToResponseTopic {
        type Destination = Names;

        fn apply(
            &self,
            out: &mut Outgoing<'_>,
            _options: &mut Option<Options>,
            cx: &PublishContext<'_, C>,
        ) {
            if let Some(topic) = cx.headers().reply_to() {
                out.set_name(topic.to_owned());
            }
            if let Some(id) = cx.headers().correlation_id() {
                out.headers_mut().insert("correlation-id", id.to_owned());
            }
        }
    }

    fn app() -> impl App<State = ()> {
        RustStream::new(AppInfo::new("device-agent", "0.1.0")).with_broker(
            MqttBroker::new("mqtt://localhost:1883", "device-agent-dev42"),
            |b| {
                // A query without a response topic is answered on the topic named here.
                let answer = subscriber("devices/dev42/config/get", Answer)
                    .reply()
                    .to("devices/dev42/config")
                    .build();
                b.include(answer)
                    .out_reply(Publish::default())
                    .transform(ToResponseTopic);
            },
        )
    }

    fn main() -> ExitCode {
        run_main(app)
    }

    ToResponseTopic 是回复位置上的一个发布转换。 它读取请求的消息头：reply-to 成为答复的主题，correlation-id 被复制到答复上。 它声明 Destination = Names，从而获得选择主题的权利。 没有 reply-to 的请求保留挂载点的主题。

    服务的 AsyncAPI 文档把回复的地址报告为请求的 reply-to 消息头 $message.header#/reply-to，因为答复不在任何固定的通道上。

    从命令行提问​

    请求方可以是任何 MQTT 5 客户端。 Mosquitto 自带一个：mosquitto_rr，它发布带响应主题的请求并打印答复：

    docker compose exec mosquitto mosquitto_rr \
      -t devices/dev42/config/get -e consoles/c1/responses -m '{"key":"firmware"}'

    它打印 {"key":"firmware","value":"2.1.0"}。 RustStream 服务中的请求方发布请求时设置这两个消息头，并用自己响应主题上的订阅者读取答复。

    测试应答者​

    示例文件中的测试在进程内发布一条带 reply-to 和 correlation-id 消息头的查询。 这些消息头到达处理器时，经过的是与线上相同的 MQTT 5 属性映射。 测试检查 consoles/c1/responses 上带关联数据的答复、没有响应主题的查询所用的后备主题，以及未知设置得不到答复。
