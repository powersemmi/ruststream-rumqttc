# Качество обслуживания

MQTT подтверждает доставку одним пакетом протокола при QoS 1 и обменом из четырёх пакетов при
QoS 2; этот крейт отправляет подтверждение, когда обработчик завершил работу.

<Diagram name="qos" words={words} />

Качество обслуживания выбирается дважды: издатель выбирает его для своего сообщения, а подписка -
для того, что она принимает. Доставка идёт на меньшем из двух уровней, поэтому публикация с QoS 0
доходит до подписки с QoS 1 на уровне QoS 0. [`Qos`](../../components/subscriptions/qos.md)
дескриптора задаёт сторону подписки, а [политика публикации](../../components/publishing/index.md) -
сторону сообщения.

При QoS 0 сервер отправляет PUBLISH и забывает о нём. Обратно ничего не передаётся, поэтому у
доставки с QoS 0 нечего подтверждать: `ack` возвращает `AckError::Unsupported`, и рантайм
записывает это в журнал.

При QoS 1 и QoS 2 сервер хранит сообщение, пока сервис не ответит. Этот крейт подключается с
ручными подтверждениями, поэтому `rumqttc` передаёт каждый PUBLISH подписке и сам ничего не
отправляет. [Подтверждение](../../components/settlement/index.md) уходит, когда доставка
подтверждена, после возврата из обработчика: PUBACK при QoS 1, PUBREC при QoS 2. PUBREL и PUBCOMP,
которые завершают QoS 2, `rumqttc` передаёт сам.

В MQTT нет отрицательного подтверждения. Доставка с QoS 1 или QoS 2, которую сервис так и не
подтвердил, остаётся на сервере. Сервер отправляет её повторно, с пометкой дубликата, только
когда постоянная сессия возобновляется на новом соединении. Это возобновление показывает страница
[Сессии](sessions.md), а что отправляет каждый исход обработчика - страница
[Завершение](../settlement.md).

При подключении клиент объявляет Receive Maximum: сколько доставок с QoS 1 и QoS 2 он принимает
без подтверждения. Когда столько доставок ждут подтверждения, сервер не отправляет по этому
соединению новых сообщений с QoS 1 и QoS 2, пока одна из них не подтверждена. По умолчанию этот
крейт объявляет 1000, а [`receive_maximum`](../../components/broker/limits.md) меняет это число.
Окно ограничивает число сообщений, которые ждут медленную подписку. Доставки с QoS 0 в нём не участвуют.

Публикация из сервиса возвращает управление, когда `rumqttc` поместил сообщение в свой канал
запросов на 64 запроса, а не когда сервер его подтвердил. `rumqttc` хранит каждую публикацию с
QoS 1 и QoS 2, пока сервер её не подтвердит. После переподключения он отправляет их повторно, если
сервер сообщает, что сессия сохранилась. Переподключение, которое начинает новую сессию,
отбрасывает их вместе с запросами, которые ещё ждут в канале.

Порядок обмена задаёт сам протокол, разделы 4.3 и 4.9
[стандарта MQTT 5.0](https://docs.oasis-open.org/mqtt/mqtt/v5.0/os/mqtt-v5.0-os.html).
