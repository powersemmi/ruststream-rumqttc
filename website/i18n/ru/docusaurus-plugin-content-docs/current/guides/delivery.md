# Гарантии доставки

Это руководство выбирает качество обслуживания для каждой подписки, показывает, что каждый исход обработчика отправляет серверу, и сохраняет сообщения, которые сервис пропускает, пока остановлен.

Пример - сервис расчётов.
Счётчики сообщают о расходе энергии, и каждый отчёт - это деньги, поэтому терять их нельзя.
Ещё они сообщают о потребляемой мощности для графика в реальном времени, где потерянный замер заменяет следующий.

## Качество обслуживания

В MQTT три уровня [качества обслуживания](../components/subscriptions/qos.md):

| Уровень | Гарантия | Пакеты протокола |
|---|---|---|
| `Qos::AtMostOnce` (0) | не более одного раза: сообщение может потеряться | `PUBLISH` |
| `Qos::AtLeastOnce` (1) | хотя бы один раз: сообщение может прийти дважды | `PUBLISH`, `PUBACK` |
| `Qos::ExactlyOnce` (2) | ровно один раз между двумя сторонами | `PUBLISH`, `PUBREC`, `PUBREL`, `PUBCOMP` |

Подписка называет уровень, на котором она читает, а издатель - уровень, на котором отправляет.
Доставка идёт на меньшем из двух.
Поэтому счётчик, который публикует расход с `QoS` 1, доходит до подписки с `QoS` 2 на уровне `QoS` 1.

Брокер подтверждает доставку, когда обработчик возвращает управление, а не когда она приходит.
Каждый [исход](../components/settlement/index.md) отправляет то, что для него есть в протоколе:

- `ack` отправляет `PUBACK` при `QoS` 1 и `PUBREC` при `QoS` 2. Обмен `QoS` 2 клиент доводит до конца сам.
- `drop` тоже подтверждает: отрицательного подтверждения в MQTT нет, и подтверждение - единственный способ закончить работу с сообщением.
- [`retry`](../components/settlement/retry.md) ничего не отправляет. Отчёт остаётся неподтверждённым, и сервер доставит его повторно, только когда сессия сервиса возобновится на новом соединении.

У доставки с `QoS` 0 подтверждения нет совсем.
Её исход возвращает `AckError::Unsupported`, и рантайм пишет предупреждение в журнал.

`bill` возвращает `retry`, когда учётная система не отвечает.
Тогда отчёт ждёт следующей сессии: после перезапуска сервер передаст его снова.
Как попробовать снова в той же сессии, показывает руководство [Переобработка и темы dead-letter](retries.md).

Обработчик, который принимает срез, - это [пакетный обработчик](../components/subscriptions/batches.md).
Пакет протокола `PUBLISH` содержит одно сообщение, поэтому пакеты брокер собирает на стороне клиента.
Пакет закрывается, когда в нём набирается размер, указанный в точке монтирования, или через 20 миллисекунд после первого замера.
Подтверждение остаётся у каждой доставки своим.

[Сессия](../components/broker/session.md) - это то, что сервер хранит для одного идентификатора клиента: его подписки и неподтверждённые сообщения с `QoS` 1 и 2.
[`clean_start(false)`](api:ruststream_rumqttc::MqttBroker::clean_start) возобновляет сессию, которую сохранил сервер, вместо того чтобы начать новую.
[`session_expiry`](api:ruststream_rumqttc::MqttBroker::session_expiry) - сколько сервер хранит её после отключения сервиса, здесь сутки.
Пока сервис остановлен, сервер копит в очереди сообщения с `QoS` 1 и 2, которые подходят к его подпискам.
Когда сервис снова подключается с тем же идентификатором клиента, сервер первыми отправляет их.
Брокер придерживает их, пока не откроется подписка, которой они принадлежат, поэтому при запуске ни одно не теряется.
Идентификатор клиента - это имя сессии, поэтому каждому процессу сервиса нужен свой. Руководство [Подключение к промышленному серверу](production.md) задаёт свой идентификатор каждому развёртыванию.

По умолчанию Mosquitto не копит сообщения с `QoS` 0 для отсутствующей сессии.
Замеры, опубликованные, пока сервис остановлен, пропадают, и графику в реальном времени это и нужно.

## Управление потоком

[`receive_maximum(100)`](../components/broker/limits.md) сообщает серверу, сколько доставок с `QoS` 1 и 2 сервис принимает, прежде чем подтвердит одну из них.
Достигнув предела, сервер перестаёт отправлять, пока обработчик не завершит какую-нибудь доставку.
Значение по умолчанию - 1000.
Неподтверждённая доставка занимает своё место в этом окне до конца соединения, поэтому каждый `retry` без объявленного предела попыток отнимает одно место до следующей сессии.
У доставок с `QoS` 0 такого окна нет: если обработчик медленнее своих издателей, их сообщения копятся в памяти без ограничения.

## Проверка гарантий

Внутрипроцессные тесты проверяют, как `bill` завершает каждый отчёт и что три замера, опубликованные разом, приходят одним пакетом.
Сессия, её возобновление и окно Receive Maximum существуют только на сервере, поэтому один тест работает на Mosquitto:

```bash
MQTT_TEST_URL=mqtt://localhost:1883 cargo test -- --test-threads=1
```

Он запускает сервис, обрывает его соединение, публикует отчёт о расходе, пока сервис остановлен, и снова запускает сервис с тем же идентификатором клиента.
Отчёт, опубликованный в отсутствие сервиса, `bill` получает первым.
Без `MQTT_TEST_URL` тест сразу завершается.
Этот приём показывает руководство [Тестирование сервиса на MQTT](testing.md).
