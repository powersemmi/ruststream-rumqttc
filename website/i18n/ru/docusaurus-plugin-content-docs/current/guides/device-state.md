# Состояние устройств: сохранённые сообщения и последняя воля

Это руководство хранит текущее состояние каждого устройства на сервере, чтобы читатель, который подключается позже, сразу его видел, и сообщает, работает ли сам сервис.

Истории MQTT не хранит, за одним исключением: [сохранённого сообщения](../components/publishing/retained.md).
Сервер хранит последнее сохранённое сообщение каждой темы и отправляет его каждой новой подписке, фильтр которой подходит к этой теме.
[Последняя воля](../components/broker/last-will.md) - это сообщение, которое сервер публикует за клиента, если его соединение завершилось без штатного отключения.

Пример - монитор шлюзов.
Шлюзы периодически присылают сигналы присутствия (heartbeat) с уровнем заряда батареи.
Сервис хранит состояние каждого шлюза, `ok` или `low-battery`, сохранённым сообщением в `gateways/<id>/state`, а панели мониторинга читают его оттуда.

Состояние - это простой текст, который панель показывает как есть. Поэтому у `GatewayState` стоит `#[derive(Serialized)]`, тип сам хранит свои байты, а кодек к ним не применяется.
Его тема - шаблон имени: `{gateway}` становится сеттером, поэтому `.to().gateway(..)` указывает тему одного шлюза.
`track` публикует состояние шлюза, от которого пришёл сигнал.

`forget` публикует пустую полезную нагрузку в тему состояния шлюза, который выводят из эксплуатации.
Пустое сохранённое сообщение удаляет сохранённое сообщение своей темы, и сервер перестаёт отдавать это состояние новым подписчикам.

[`retain(true)`](api:ruststream_rumqttc::MqttPublish::retain) в [политике публикации](../components/publishing/index.md) делает сохранённой каждую публикацию через слот.
Оба обработчика используют слот `States` и одну политику, поэтому состояние и его удаление публикуются одинаково.
Сохранённым можно сделать и отдельное сообщение: [шаг `retain`](../components/publishing/mqtt-publish-steps.md) у публикации переопределяет политику для этого вызова.

Совместная подписка не получает сохранённых сообщений, когда подписывается.
Панель, которая читает состояния, подписывается вне любой группы совместной подписки.

[`last_will`](api:ruststream_rumqttc::MqttBroker::last_will) принимает тему, полезную нагрузку, качество обслуживания и флаг сохранения последней воли.
Брокер передаёт последнюю волю серверу при подключении.
Если соединение завершается без пакета протокола `DISCONNECT`, потому что процесс аварийно завершился или отказала сеть, сервер публикует последнюю волю: здесь `offline`, сохранённым сообщением в `services/gateway-monitor/status`.
Штатная остановка отправляет `DISCONNECT`, и сервер отбрасывает последнюю волю.

Вторая половина - хук `after_startup` в приложении выше.
Он выполняется, когда брокер подключён, и публикует `online` сохранённым сообщением в ту же тему.
Поэтому в теме статуса всегда лежит последнее из двух, и подписавшаяся панель сразу его читает.

## Проверка состояния

Внутрипроцессные тесты проверяют, что публикует сервис: состояние каждого шлюза, пустую полезную нагрузку для удалённого шлюза и `online` при запуске.
Внутрипроцессный сервер хранит сохранённые сообщения так же, как Mosquitto.
Последнюю волю публикует сервер, когда соединение обрывается, поэтому один тест работает на Mosquitto:

```bash
MQTT_TEST_URL=mqtt://localhost:1883 cargo test -- --test-threads=1
```

Он запускает сервис, штатно останавливает его и после этого запускает панель: панель получает `online` и состояние шлюза, оба сохранённые.
Затем он завершает очередной запуск сервиса без `DISCONNECT`, и панель получает `offline`.
В конце он удаляет шлюз теста, и его состояние на сервере стирается.
