# Публикация команд

Это руководство отправляет команды одному устройству из многих, с тем качеством обслуживания, которое нужно каждой команде, и с заголовками, которые прочитает устройство, написанное на любом языке.

Пример - сервис-диспетчер команд.
Операторы отправляют запрос команды в `operators/commands`.
Сервис пересылает каждую команду в тему её устройства, `devices/<id>/commands`.

Тема `DeviceCommand` - шаблон имени.
`{device}` становится сеттером публикации, поэтому обработчик называет устройство, а тема строится из него.
`Commands` - слот, через который публикует обработчик, и публикует он только `DeviceCommand`.

Политика слота задаёт качество обслуживания каждой команды.
Для срочной команды вызывается [шаг `qos`](../components/publishing/mqtt-publish-steps.md), и она уходит с `QoS` 2.
Шаг меняет одно сообщение. Настройку, которую вызов не называет, берёт политика.
Шаг записывает [`MqttPublishOptions`](api:ruststream_rumqttc::MqttPublishOptions), поэтому ограничение слота называет этот тип, а файл импортирует прелюдию брокера.
Второй шаг - `retain`, и руководство [Состояние устройств](device-state.md) задаёт его в политике.

Заголовок `operator` передаётся [пользовательским свойством](../components/publishing/headers.md) MQTT 5.
Устройство читает его как обычное свойство, без конверта вокруг полезной нагрузки.
Заголовки `content-type`, `reply-to` и `correlation-id` вместо этого занимают собственные свойства протокола: тип содержимого, тему ответа и данные корреляции.

`publish` возвращает управление, как только сообщение принял клиент, до подтверждения от сервера.
При `QoS` 1 и 2 клиент отправляет сообщение повторно, пока сервер его не подтвердит, в том числе после переподключений.
Ошибка из `publish` означает, что клиент не принял сообщение: соединение закрыто или сообщение нарушает правила протокола.
Тема с `+` или `#` их нарушает: запрос называет устройство `+`, тема становится `devices/+/commands`, и `dispatch` отбрасывает запрос.
Заголовок или тема с управляющим символом отклоняются так же, потому что сервер может закрыть соединение из-за такого символа.

Точка монтирования задаёт слоту политику с `QoS` 1 и преобразование публикации.
`Json` ставит `content-type: application/json` на каждую команду, которую отправляет слот.
Брокер превращает заголовок в свойство типа содержимого и выставляет индикатор формата полезной нагрузки, поэтому устройство читает тело как текст в UTF-8.
Сам кодек этот заголовок не пишет: тип содержимого сервис указывает один раз, преобразованием в точке монтирования.

## Проверка команд

Тесты в файле примера запускают приложение внутри процесса и читают команды, которые опубликовал слот.
`tb.out::<Commands>()` показывает настройки каждого сообщения: никаких у обычной команды и `QoS` 2 у срочной.
`published` в `devices/dev42/commands` показывает полезную нагрузку и оба заголовка.
Внутрипроцессный сервер проверяет темы и заголовки так же, как клиент, поэтому запрос для устройства `+` отбрасывается и там.
